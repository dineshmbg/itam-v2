Yes, I've built this: a Software update page under Data tools, next to Data import. I tested the page and every step of the updater. The Podman and systemd pieces on your real VM are untested, because I can't reach it.

How you'll use it:

On your PC: run .\deploy\build-release.ps1. It runs the tests, builds the image and signs it, producing deploy\releases\itam-release-<version>.itamrel.
In the portal, as an administrator: open Data tools → Software update, choose that file and press Upload. The page checks it and lists it. You can also copy the file into /var/lib/itam-updates/incoming/ on the VM and it appears in the same list.
Press Install…, read what will happen, and type UPDATE. Progress shows live on the same page, and the page reconnects by itself while the portal restarts.
Go back later: the page also has a Go back to <previous version> button.
What runs after you confirm:

It checks the signature and the image checksum again.
It backs up the database.
It loads the new image and restarts the portal.
It waits until the new version is healthy.
If it isn't healthy, it puts the old version back on its own, and the page says "Rolled back".
Why nobody can push the wrong thing: only files signed with your private key are ever installed. I created that key on this PC at C:\Users\dines\.itam-release\release-private.pem. Copy it to a USB stick and keep it safe. If you lose it, no new package can be signed until a new key is installed on the VM. Your portal admin logins can't install anything unsigned either.

Why there's a separate service on the VM: the portal runs inside a container and can't restart itself. A small service on the VM, running outside the container, does the risky steps. It re-checks everything and doesn't trust the portal.

Database changes: new tables and columns are applied automatically when the new version starts. Your data is never replaced.

One-time switch-over for your existing VM:

Copy the deploy folder to the VM.
Run sudo DB_HOST=10.205.64.46 ./vm-install.sh once. It installs the update service, your public key and the first new image.
After that, every update is done from the page. The page shows "Update service running" when the VM side is alive.

I wrote the guide as deploy/STEP-BY-STEP-GUIDE.md. Every step is tagged with where to run it: [DEV PC], [SERVER] (Windows Server 2019, 10.205.64.46), [VM] (Ubuntu, 10.205.64.25), or [BROWSER]. I have not run any of it on your real servers.

The parts, in order

Part 1, [DEV PC]: run .\deploy\build-release.ps1. It builds a fresh signed release.
Part 2, [SERVER]: back up the database, then run Prepare-Database.ps1 -VmAddress 10.205.64.25 -ConfigureNetwork to confirm the VM may connect. It is safe to repeat and never touches your data. Then check PostgreSQL and set the VM to start with the server.
Part 3, [DEV PC] to [VM]: copy the deploy folder across with scp.
Part 4, [VM]: run sudo DB_HOST=10.205.64.46 TLS_NAMES=10.205.64.25 bash ./vm-install.sh once. This installs the update service and switches the VM to the new version. It has pre-flight checks and verification commands.
Part 5, [BROWSER] and [VM]: trust the certificate, first sign-in, and the commands to recover administrator access.
Part 6, [DEV PC] and [BROWSER]: every later update, done from the portal. Build the release, upload it in the browser, press Install, and type UPDATE.
Part 7: going back to the previous version, from the portal or from the VM if the portal is down.
Part 8: a routine schedule of what to keep running.
Part 9: troubleshooting, by symptom, with which machine to look on.
Appendices: a command cheat sheet per machine, and a from-scratch variant for a brand-new server.
